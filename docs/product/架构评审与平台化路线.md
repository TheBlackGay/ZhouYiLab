# ZhouYiLab 架构评审与平台化路线

> 维护日期：2026-09-18　评审基线：`r_2.0.0` 分支（HTTP API `v1`，`algorithm_version = zhouyilab-core/1.4.1`）
>
> 定位前提：ZhouYiLab 是**中国传统文化工具平台**——以术数排盘与解读为核心工具集，向内部页面和外部项目同时提供 JSON API。本文记录架构现状、优势资产、风险缺口，以及分阶段的平台化演进路线。

---

## 1. 总体架构现状

当前实际形态是 **"C++ 术数算法内核 + Python 解读/服务层 + 无框架 Web 前端"的单体工具平台**：

```text
┌─────────────────────────────────────────────────────────┐
│  浏览器前端（原生 HTML/CSS/JS 多页面）                      │
│  index(紫微) qimen bazi liu-yao da-liu-ren astro          │
│  blind-review ai-review + place-picker 地点选择器          │
├─────────────────────────────────────────────────────────┤
│  HTTP 服务层  web/server.py（约 900 行，stdlib 单文件）     │
│  ThreadingHTTPServer；if 链路由 26 处判断；                 │
│  统一响应包 {success, data, meta{api_version,              │
│  algorithm_version, request_id}}；默认监听 127.0.0.1:8768  │
├──────────────┬──────────────────────────────────────────┤
│ Python 解读层│  ziwei_pattern_engine(格局匹配, 36 谓词)     │
│ （规则+研究）│  ziwei_analysis / ziwei_brightness           │
│              │  ziwei_ai_review / blind_review / research  │
│              │  astro_analysis / daily_reading /           │
│              │  natal_analysis / natal_reading / transit   │
│              │  geo_places（地点解析 + tzdata 时区）        │
├──────────────┴──────────────────────────────────────────┤
│  进程边界：JSON CLI（stdin → stdout，按请求 subprocess 拉起）│
│  zi_wei / qi_men / ba_zi / liu_yao / da_liu_ren /         │
│  common_calendar / astro  共 7 个 Web CLI                  │
├─────────────────────────────────────────────────────────┤
│  C++23 Modules 算法内核  ZhouYiLabCore（约 34K 行）         │
│  功能层: ZiWei(30 文件) BaZi QiMen LiuYao DaLiuRen Astro   │
│  公共层: Common.DateTime / Common.Calendar / GanZhi        │
```

部署链路：多阶段 Dockerfile（`silkeh/clang:20` 构建 7 个 CLI → `ubuntu:24.04` 运行 Python 服务）+ docker-compose + `scripts/deploy-zhouyilab-183.sh` 一键部署；生产域名 `zhouyilab.k8s.gold`（nginx 反代），内网直连 `192.168.31.183:8768`；CI 覆盖 clang / GCC(MSVC) 多编译器构建。

**领域分层现状（按能力而非代码目录）**：

| 层 | 承载 | 现状 |
| --- | --- | --- |
| 历法/天文基础 | tyme4cpp、Common.Calendar、Swiss Ephemeris | 已收敛到单一公共层，含真太阳时、均时差、公农历互转 |
| 排盘事实 | 7 个 C++ Web CLI | 全部经 JSON CLI 边界输出，接口契约有回归测试 |
| 规则解读 | Python 格局引擎 + astro 规则模块 + C++ 神煞 + 前端奇门提示 | **仅紫微完成声明式化**，其余各写各的 |
| 语言表达 | 页面文案、断语卡片、AI 预评审 | 有"AI 只组织事实"的边界约束 |
| 研究验证 | 盲评 + AI 多模型评审 + SQLite 留档 | 协议 JSON 化，是差异化资产 |

## 2. 架构优势资产（应当保持和放大）

### 2.1 "事实 / 规则 / 语言"三层分离

C++ 只产出排盘事实；Python 声明式引擎只做规则匹配并输出完整条件追踪；断语与 AI 只做语言组织，且明确"AI 不得重新排盘或发明格局"（README 设计原则）。每条结论可回溯到"哪个规则、哪个条件、盘上哪个证据"。这是术数软件最稀缺的**可信度架构**，也是平台区别于普通排盘 App 的护城河。

### 2.2 跨语言防腐层极窄

C++ ↔ Python 之间只有"JSON CLI（stdin/stdout）"一种接口。内核不依赖 HTTP 库，Python 不依赖 C++ ABI；`tests/test_*_web_contract.py` 直接锁契约。低成本但有效。

### 2.3 公共能力抽取有纪律

`docs/common/公共能力与组件设计.md` 确立了"先登记复用、再决定抽取""公共层禁止依赖功能模块""语义不同的不抽"三条边界。日期校验、tyme 适配、真太阳时、公农历互转已单点化。

### 2.4 "校准状态"是一等公民

"已有实现 ≠ 已校准"写入 README 状态表（紫微/奇门已校准、八字校准中、六爻/六壬待校准）；API meta 带 `algorithm_version`；发布分支按 `r_x.y.z` 版本线走；八字侧有《神煞全量审计报告》《神煞校准流程》。可信度分级本身就是平台能力。

### 2.5 研究工具链

匿名盲评包、维度量尺、AI 多模型重复实验（Ollama/OpenAI 兼容、温度/种子控制）、SQLite 留档，把"算法是否靠谱"变成可量化流程。同类开源项目中几乎独有。

## 3. 风险与缺口（对照工具平台定位）

| # | 风险 | 现状证据 | 影响 |
| --- | --- | --- | --- |
| R1 | **每请求 fork 引擎进程** | `server.py::run_engine` 对每个 API 请求 `subprocess.run` 拉起 CLI（20s 超时）；ThreadingHTTPServer 线程数无上限 → 子进程数也无上限 | 冷启动开销大；突发流量下 CPU 过订阅；无排队/降级；QPS 天花板先到这里 |
| R2 | **公网服务面无治理层** | 无鉴权、无限流、无 API Key，仅靠反代暴露 `zhouyilab.k8s.gold`；README 已承诺"其他项目以该域名为 Base URL" | 外部接入不可计量、不可配额，事故无法归因 |
| R3 | **单文件承载四种职责** | server.py 同时是静态站、API 网关、规则分析编排、研究工具后端 + SQLite 留档入口；26 处 if 路由链 | 页面/接口/研究迭代互相牵连，回退粒度粗，与 2.x"独立验证、部署、回退"目标矛盾 |
| R4 | **声明式规则红利只覆盖紫微** | 格局引擎 36 个谓词全在 `ziwei_pattern_engine.py`；八字神煞在 C++ 硬编码；astro 规则硬编码在 `astro_natal_analysis.py`（551 行）；奇门学习提示硬编码在前端 `qimen_learning.js` | 每新增一门术数就重新发明一次"规则放哪、怎么匹配、证据怎么输出" |
| R5 | **领域知识三处双写** | 星曜名/亮度语义同时存在于 C++ 枚举、`config/ziwei/*.json`、Python 引擎 | 口径漂移靠测试兜底；新术数接入成本随模块数上升 |
| R6 | **无平台记忆层** | 除研究 SQLite 外不持久化任何排盘；无历史、分享、缓存 | 2.x 有意不做账号是合理取舍，但平台阶段需补 |
| R7 | **前端多页复制粘贴** | 每工具一套 html/css/js；`app.js` 41K；已有 `app-shell.css` / `navigation.js` 雏形 | 工具从 8 涨到 20 时不可维护 |
| R8 | **容器文件权限隐患** | `web/` 下 `astro_natal_analysis.py`、`astro_natal_reading.py`、`geo_places.py`、`place-picker.js/css`、`requirements.txt` 为 600 权限，Docker 运行时以 uid 10001 读入 | 特定 umask 下镜像可能起不来，属发布事故级 |

## 4. 演进路线（优化版）

> **实施状态（2026-09-18）**：P0 全部四 items 已落地并通过 298 项回归。
>
> * P0-1：`web/tool_registry.py` + `config/platform/tools/*.json`（7 工具清单 + schema）；
>   奇门/八字/六爻/大六壬排盘路由已收敛为清单分发（`server.py` 删除 4 条同构分支）；
>   新增 `GET /api/v1/tools`；health 追加 `registry_source` 与 `tools` 校准状态；
>   启动门槛改由 `required_at_startup/optional_env` 推导（calendar 缺失不再阻塞启动）。
>   内建默认保留为回退路径，P1 引入常驻引擎池后择机移除。
> * P0-2：`web/governance.py`；默认 `observe`（只记录不拦截），访问日志落
>   `.zhouyilab/logs/access.jsonl`（含 request_id/耗时/治理裁决）；enforce 档
>   支持 `X-API-Key` 与每密钥令牌桶；`/api/v1/health` 豁免；无密钥 enforce 自动降级。
> * P0-3：`web/` 6 个 600 权限文件已修为 644（git 索引本为 100644，属本地漂移）；
>   Dockerfile 增加 `chmod -R a+rX` 兜底；新增 `.github/workflows/docker-smoke.yml`
>   （镜像构建→容器启动→health/tools/symbols/ziwei 排盘冒烟）。
> * P0-4：紫微 CLI 新增 `symbols` operation（内核权威符号集：星名 109、亮度 7、
>   四化 4、十二宫、干支五行），`GET /api/v1/ziwei/symbols` 透传并进程级缓存；
>   回归测试锁定 `symbolism_dictionary.json ⊆ 内核符号集`。
>   **审计发现（待校准处理，非 P0 范围）**：杂曜文档库键"截空"与枚举名
>   "截路/空亡"口径不一致（`zi_wei_star_doc_za_yao.cpp`），symbols 已按并集
>   兼容输出，但文档键名应在下一次紫微内容校准中显式定口径。

原则：**不推倒重来，每一步都能独立上线、验证、回退**（与 2.x 发布门槛一致）。先还债定标准，再动进程模型，最后拆服务。

### 阶段 P0：平台契约与低息债（1～2 周，无架构变动）

#### P0-1 工具接入规范（Tool Manifest）——平台化的第一份合同 ✅ 已实施

- **问题**：新增一门术数要改 server.py 路由链、前端目录、Docker 目标、README 表格共四处，"平台"没有注册机制。
- **方案**：新建 `config/platform/tools/<tool>.json`，每工具一份清单：

  ```json
  {
    "id": "da_liu_ren",
    "engine_cli": "build/examples/da_liu_ren_web_cli",
    "api_prefixes": ["/api/v1/da-liu-ren/"],
    "pages": ["da-liu-ren.html"],
    "rules_dir": "config/daliuren/rules",
    "calibration_status": "pending",
    "meta_endpoint": "/api/v1/da-liu-ren/meta"
  }
  ```

- **实现要点**：server.py 增加启动期加载器，把 26 处 if 链收敛为 `path 前缀 → handler` 注册表；manifest 校验失败则拒绝启动（fail-fast）。现有路由行为逐条快照测试后再迁移，**一次只迁一条路由**。
- **验收**：新增一门"echo 假工具"只加 manifest + 一个 handler 函数即可出现在 `/api/v1/health` 引擎清单中；全部既有 contract tests 绿色。
- **回退**：注册表读不到 manifest 时回落原 if 链（保留一个大版本）。

#### P0-2 公网最小治理层 ✅ 已实施

- **方案**：反代或 server.py 中间件加三件事：`X-API-Key` 白名单（先只区分 internal/external 两档）、per-key 令牌桶限流、访问日志（复用已生成的 `request_id`，JSON Lines 落 `.zhouyilab/logs/access.jsonl`）。
- **验收**：无 key 请求默认 403（页面同源请求免 key 或走 internal key）；限流命中返回 429 + `Retry-After`；日志可按 request_id 串起 CLI 耗时。
- **风险控制**：先"只记录不拦截"上线一周观察误杀，再开启拦截。

#### P0-3 权限与构建修复 ✅ 已实施

- `git update-index --chmod=644` 修正 600 权限文件；Dockerfile 加一行 `RUN chmod -R a+r web config data` 兜底；CI 的 docker build 后补 `docker run --rm -p …:8768 … && curl /api/v1/health` 冒烟。

#### P0-4 符号字典单源化 ✅ 已实施

- **问题（R5）**：星曜名、亮度、干支中文名在 C++/config/Python 三处存在。
- **方案**：由 C++ 内核新增 `symbols_web_cli`（或现有 calendar CLI 加 operation），导出 `symbols.json`（星曜、亮度、四化、干支、宫位枚举全集）；Python 引擎加载时校验配置中星名 ∈ 字典（紫微侧已有 `known_star_names` 雏形，推广为全平台）；前端下拉框同样从 `/api/v1/meta/symbols` 取数。
- **验收**：拼错星名的规则配置在加载期报错，而不是匹配期静默不命中。

### 阶段 P1：引擎调用模型升级（2～4 周，性能天花板解除）

#### P1-1 常驻引擎池（warm worker pool）

- **问题（R1）**：每请求 fork C++ 进程，模块加载 + Swiss Ephemeris 初始化重复付费；线程无上限 → 子进程无上限。
- **方案**：给 7 个 CLI 加 `--serve` 模式：进程常驻，按行读 stdin 的 JSON 请求（NDJSON），逐行写响应，保留一次性模式兼容现有测试。Python 侧实现 `EnginePool`：每引擎 N=2 个 warm worker + 请求队列 + 单 worker 超时后隔离重启；请求总数上限沿用现 20s 超时语义。
- **实现要点**：
  - 协议只加一帧：`{"id": <n>, ...原请求}` → `{"id": <n>, ...原响应}`，CLI 一次性模式与 serve 模式共用同一处理函数，杜绝双实现漂移。
  - 池不预启动全部引擎：按 manifest 懒启动，健康检查只探"能否拉起"。
  - 内存护栏：worker 处理 500 请求后优雅轮换（防长尾泄漏）。
- **验收**：`/api/v1/ziwei/charts` p95 延迟对比基线下降 ≥60%；压测 50 并发不出现进程风暴；kill 单个 worker 后请求自动重路由、健康检查报 degraded 而非 down。
- **回退**：环境变量 `ZHOUYILAB_ENGINE_MODE=subprocess|pool` 一键切回旧路径。

#### P1-2 引擎耗时与错误归因

- meta 响应追加 `engine_latency_ms`；access 日志记录 CLI stderr 摘要（截断落盘）。这是后续容量规划与"哪门术数慢"的唯一数据来源，成本低，随 P1-1 一起做。

### 阶段 P2：规则平台化（4～6 周，平台核心红利）

#### P2-1 规则 DSL 升格为跨术数引擎

- **问题（R4）**：36 个谓词的格局引擎是事实上的 DSL，但语义被紫微绑死（谓词名 `star.*`/`palace.*` 直接复用）。
- **方案**：三步走，每步独立发布——
  1. **拆内核**：把 `ziwei_pattern_engine.py` 分为 `rule_engine_core`（清单加载、schema 校验、必要条件/增益/减弱/破格档位、条件追踪输出、内置案例执行）与 `ziwei_predicates`（36 谓词实现）。行为零变化，靠现有 1309 行引擎的全部测试保证。
  2. **定契约**：统一证据包结构 `rule-hit/1.0`：`{rule_id, rule_version, status, tier, matched_subform, evidence[{predicate, params, observed, source}]}`。紫微输出先迁移到该结构（对外字段兼容保留）。
  3. **再推广**：八字神煞、astro 规则、奇门学习提示按此 DSL 各迁一批"高频且口径稳定"的规则。**不追求全量迁移**——每迁一条都要带正反案例进 `_manifest.json`，由 CI 跑 `run_catalog_examples` 门禁。
- **验收**：同一引擎进程可加载 `config/ziwei/patterns/` 与 `config/bazi/rules/`；八字 API 输出含条件追踪证据包；删除任一规则 JSON 只影响该条命中。

#### P2-2 校准流水线门禁

- **问题（R5/可信度）**："校准状态"目前靠 README 人工表格。
- **方案**：manifest 中 `calibration_status` 由构建期生成：工具规则库全部案例通过 → `calibrated`，存在 `pending_boundary` 标记案例 → `in_review`，否则 `pending`。API meta 与健康检查直接暴露，前端页面横幅同步展示（页面已按"只呈现已校准事实"执行，如八字页，将此规则机器化）。
- **验收**：故意让一条规则案例失败，CI 阻断发布且 health 降级可见。

#### P2-3 古籍出处引用（知识层起步）

- 规则 schema 已有"来源说明"惯例；升级为 `source: {book: "毕法赋", chapter: "…", doc: "docs/daliuren/毕法赋.md#L…"}`。前端证据卡可点开原文。`docs/` 里的古籍资产（毕法赋、64 课、安星诀、神煞全量审计）由此变成产品体验："每条断语可查出处"。

### 阶段 P3：服务面拆分与平台记忆（2.x 收尾后择机）

#### P3-1 前端工具页骨架组件化

- 三槽位组件：输入面板（日期 + place-picker + 真太阳时校正，一次抽自现有页面）→ 盘面渲染器（每术数唯一要写的部分）→ 证据/解读卡片流（消费 P2-1 证据包，天然通用）。大六壬 2.0 页面（路线图样板）直接用骨架实现，验证复用路径。

#### P3-2 服务拆分（只拆两处，克制）

- `research`（盲评 + AI 评审 + SQLite 留档）拆为独立进程/容器：它安全等级最高（持有模型 API Key）、流量模式最特殊（长任务）、与排盘 API 无耦合。
- 静态页面交给反代直接服务（或 `nginx -p web/`），server.py 只留 API。
- 明确**不拆** engine-gateway 与 rule-service：P1 的池 + P2 的 core 已是进程内清晰边界，提前拆成两个 HTTP 服务只会把 JSON 边界变成两次网络序列化。

#### P3-3 平台记忆层（进入 3.x 时启动）

- 排盘输入规范化后取哈希做缓存主键（同输入 + 同 `algorithm_version` → 直接返回），SQLite 起步即可，与 research 库分文件。
- 在此之上有分享链接、历史记录、跨术数同刻对比（2.4.0 的"跨术数统一"正是它的入口）；账号体系仍是最后的选项，不着急。

## 5. 与大六壬 2.0 样板的合流点

2.x 路线图把大六壬定为可交付样板，建议样板范围在既有交付门槛上**追加四项**，让"接入一门新术数"的标准路径在 2.0 里就走通：

1. 大六壬是第一个使用 **tool manifest**（P0-1）注册的工具；
2. 大六壬页面使用**前端骨架三槽位**（P3-1 提前在样板上首次实现，哪怕后续再打磨）；
3. 大六壬的规则解释（2.2.0"规则解释版"）从第一天就产出 **rule-hit/1.0 证据包**（P2-1），不写一次性解释代码；
4. 六壬校准案例进入 **CI 门禁**（P2-2），替代人工状态表。
