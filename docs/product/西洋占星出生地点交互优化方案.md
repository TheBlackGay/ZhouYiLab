# 西洋占星出生地点交互优化方案

> 前置方案：[西洋占星本命盘布局解读设计方案](西洋占星本命盘布局解读设计方案.md)（N1-N5，N1-N4 已交付）
> 本方案编号 G1-G3，只改「出生地点」的**输入体验与时间口径**。
> 硬约束：不改排盘算法、不改 `/api/v1/astro/charts` 请求体、不改 N1-N4 的解读口径与现有 205 项测试基线。
> 定位：本方案交付的是**全系统共用的出生地点组件**（§5），G1 阶段只接入西洋占星页。

## 1. 结论先行

### 1.1 现状

西洋占星页「出生地点」区块（`web/astro.html` 第 53-61 行）是三个裸数字输入：

| 字段 | 控件 | 默认值 | 用户需要知道什么 |
| --- | --- | --- | --- |
| `utc_offset_minutes` | `type=number`，步进 30 | `480` | UTC 偏移是多少分钟（不是小时，不是时区名） |
| `location.latitude` | `type=number`，步进 0.0001 | `31.2304` | 北纬/南纬靠正负号表达 |
| `location.longitude` | `type=number`，步进 0.0001 | `121.4737` | 东经/西经靠正负号表达 |

没有任何城市名、时区名、夏令时提示、解析结果回显或一致性校验。用户必须先去别处查到坐标，再自己换算 UTC 偏移，然后祈祷没算错。

### 1.2 实测影响

默认案例 `1990-05-20 14:00 · 上海` **落在 1986-1991 年中国夏令时区间内**。本地 tzdata 给出的切换点是：

```
Asia/Shanghai  1990-04-16 -> +540 分钟（UTC+9）
Asia/Shanghai  1990-09-17 -> +480 分钟（UTC+8）
```

即 1990-04-16 起进入夏令时，1990-09-16 为止，1990-09-17 恢复 UTC+8。这个案例当时用的是 **UTC+9**，而页面默认填的是 `480`。同一份出生资料，只因偏移差 60 分钟：

| 项目 | 偏移 480 | 偏移 540 | 差异 |
| --- | --- | --- | --- |
| 上升点黄经 | 179.2333°（处女 29°14′） | 166.2719°（处女 16°16′） | **12.96°** |
| 天顶黄经 | 89.1850°（双子 29°11′） | 75.3263°（双子 15°20′） | **13.86°** |
| 金星落宫 | 第 7 宫 | 第 8 宫 | 换宫 |
| 火星落宫 | 第 6 宫 | 第 7 宫 | 换宫 |
| 土星落宫 | 第 4 宫 | 第 5 宫 | 换宫 |
| 冥王星落宫 | 第 2 宫 | 第 3 宫 | 换宫 |

十大行星里 **4 颗换宫**，上升与天顶各偏 13° 左右，宫位布局发生实质变化。而 N1-N4 交付的正是「黄道与宫位布局」解读——宫位一变，半球/象限分布、空宫列表、宫位卡片、宫主星去向全部跟着变。

而且这不是孤例。把 `Asia/Shanghai` 的全部切换点扫完，历史上有过至少五段不同的偏移口径：

| 区间 | 偏移 | 性质 |
| --- | --- | --- |
| 1901-01-01 之前 | +8:05:43 | 地方平时（LMT） |
| 1919-04-14 至 1919-09-30 | UTC+9 | 夏令时 |
| 1940-06-02 至 1940-10-12 | UTC+9 | 夏令时 |
| 1941-03-16 至 1941-11-01 | UTC+9 | 夏令时 |
| **1942-02-01 至 1945-09-01** | **UTC+9** | **连续三年半，非夏令时性质** |
| 1946 / 1947 / 1948 / 1949 | UTC+9（夏季） | 夏令时 |
| 1986-05-05 至 1991-09-15 | UTC+9（夏季） | 夏令时 |

最后一行就是当前默认案例踩中的那段。第四行更能说明问题：1942-1945 年连续三年半的 UTC+9 **既不是夏令时、也不在「无/+30/+60」三档里能表达**，只有查时区数据库才拿得到。**靠人工填分钟数或选一个夏令时下拉，本质上填不对这些年份。**

### 1.3 方案一句话

把「填三个数字」改成「搜一个地名」：坐标、时区、当时的夏令时全部自动推导，推导结果连同证据一起显示在页面上，允许一键覆盖；覆盖后进入「已校正」状态，自动值不再静默改回；再用软校验拦掉明显矛盾的组合，并记住最近使用的地点。

### 1.4 分层结论

只动前端与 Python 服务层。`/api/v1/astro/charts` 的请求体保持 `utc_offset_minutes` + `location{latitude,longitude}` 不变，前端只是「帮用户把这三个数填对」。C++ 引擎、N1-N4 解读层、现有 205 项测试全部不动。

### 1.5 共用结论

出生地点**不是一个占星专属控件**。全系统 6 个页面里有 3 个需要地点，且要的字段不同（西洋占星要绝对偏移与坐标，紫微/八字要经度与标准经线）；但两组字段都能从同一次地名解析导出（§5.1 有逐项映射与公式依据）。因此本方案交付中立的解析服务与组件，**G1 只接入西洋占星页**，紫微/八字留到 G2。

## 2. 现状问题清单

| 编号 | 问题 | 具体表现 | 后果 |
| --- | --- | --- | --- |
| P1 | 时间口径无引导 | 「UTC 偏移（分钟）」要求用户知道 480 这个数；夏令时、历史时区变更完全没有提示 | 高概率算错盘（见 §1.2），且用户无从察觉 |
| P2 | 坐标需要外部查表 | 四位小数经纬度，靠正负号区分南北纬/东西经 | 用户离页查数据，容易抄错、抄反符号 |
| P3 | 无地名、无粒度 | 只能填坐标；默认值其实是「上海市中心某点」 | 用户不知道自己填的是哪个点，无法核对 |
| P4 | 无核对回路 | 输入合法即计算，页面不回显「解析成了哪个地方、哪个时区」 | 错误静默通过 |
| P5 | 无一致性校验 | 经度 121°E 配 UTC+0 也能算出结果 | 产出无意义的盘，且看不出无意义 |
| P6 | 无记忆、无分享 | 每次重进页面都要重填；不能把参数发给别人 | 重复劳动 |
| P7 | 移动端/无障碍粗糙 | 三个 number 输入、无单位后缀、spinner 步进 0.0001 无意义、无输入建议 | 手机端体验差；坐标微调几乎不可用 |
| P8 | 海拔未暴露 | 引擎已支持 `location.elevation_m`（`src/astro/astro_controller.cppm` 第 178 行 `location.value("elevation_m", 0.0)`） | 高原地区宫位/时间的细微影响无法输入（G3 补） |

同一问题在紫微斗数页（`web/index.html` 第 67-71 行）与八字页（`web/bazi.html` 第 74-78 行）也存在，但形态不同：那两页只需要经度做真太阳时校正，已经有 `.unit-input` 单位后缀与「标准经线 / 夏令时」下拉。**反过来说更刺眼**：紫微与八字页至少提供了一个夏令时下拉，西洋占星页连这个都没有；而那个下拉只有「无 / +60 / +30」三档，表达不了 §1.2 里的 1942-1945 与 LMT 段。

## 3. 设计目标

1. **可发现**：输入地名就能选到，不必知道坐标。
2. **可核对**：选完立刻显示「哪个地方 / 什么坐标 / 什么时区 / 当时实际偏移多少」，一眼能看出对不对。
3. **可覆盖**：自动推导一定是可改的；改过之后保留用户的修正，并标注「已手动校正」。
4. **可解释**：夏令时这类推导要给出理由与来源（时区库版本、切换日期），不做黑箱。
5. **有兜底**：地点库里查不到时，能退回手动坐标，且手动输入也不难填。
6. **离线可用**：地名库与时区库都在本地，不调网络地理编码服务（与「C++ 本地算法」的产品定位一致）。
7. **可共用**：解析服务与组件中立，不绑定占星语义，其他页面接入时不需要改服务。
8. **不越界**：只陈述民用地名与时区法规事实，不产生任何命理结论；推导置信度不足时明确说明。

## 4. 目标交互（西洋占星页）

### 4.1 主路径：一个地名搜索框（G1）

`02 出生地点` 区块的第一个控件从「UTC 偏移」换成一个 combobox：

```
出生地点
┌────────────────────────────────────────────────┐
│  搜索城市 / 拼音                       南      │
├────────────────────────────────────────────────┤
│ 南京市   江苏省   中国 · 118.80°E 32.06°N  [Asia/Shanghai] │
│ 南昌市   江西省   中国 · 115.89°E 28.68°N  [Asia/Shanghai] │
│ 南宁市   广西     中国 · 108.37°E 22.82°N  [Asia/Shanghai] │
│ 南阳市   河南省   中国 · 112.53°E 32.99°N  [Asia/Shanghai] │
│ 南通市   江苏省   中国 · 120.86°E 31.98°N  [Asia/Shanghai] │
────────────────────────────────────────────────┘
```

- 中文输入 1 个字即可触发；拼音/英文需 2 个字符（`shanghai`、`sh`、`上海市`、`上海` 都能命中）。
- 候选行固定四段：**地名** / **上级行政区** / **国家 + 坐标** / **时区徽标**。
- 键盘：`↑ ↓` 移动、`Enter` 选中、`Esc` 关闭、`Tab` 离开时保留输入；鼠标与触摸同样可用，无 hover-only 交互。
- 排序：前缀命中 > 子串命中；同级内按行政级别与人口降序。
- 空输入时展示「最近使用」与「常用城市」两组快捷项，避免从零开始打字。
- 无匹配时明确说明「没有找到『XX』」，并给两个出口：「手动输入坐标」/「按坐标找最近城市」。

**G1 的地名库是城市级**（§6.1 的 `curated`），所以候选是「南京市」这样的城市，不是「南京市 鼓楼区」。区县检索属于 G2，UI 在 G1 不承诺。

### 4.2 选中后：地点卡（G1）

选中候选后，搜索框下方出现一张可核对的卡片，而不是让数字散落回表单：

```
┌────────────────────────────────────────────────┐
│ 上海市                             [更换] [微调] │
│ 城市代表点 · 121.4737°E · 31.2304°N             │
│ 时区 Asia/Shanghai · 当时偏移 UTC+9（540 分钟） │
│ ⓘ 1990-04-16 起至 1990-09-16 当地实行夏令时，   │
│   1990-09-17 起恢复 UTC+8。          [为什么？] │
│ ⚠ 该地点为城市级代表点，行政范围较大时建议微调。 │
└────────────────────────────────────────────────┘
```

卡片里的三个数就是最终发给 `/api/v1/astro/charts` 的值，用户看到什么就是什么。`[更换]` 回到搜索，`[微调]` 展开 §4.3。

**一处刻意的连续性设计**：`curated` 里「上海市」的坐标就取 `121.4737°E / 31.2304°N`（与现默认值一致），所以换成新 UI 后默认案例排出的盘**与现在完全相同**——205 项测试基线与用户既有结果都不用动。

`海拔` 一行在 G1 不显示：`curated` 数据里没有海拔字段，显示「海拔 0m」会让人误以为查到了数据。G3 引入海拔后按「未提供 / 已提供」两态显示。

### 4.3 兜底：手动坐标与时区（G1）

`[微调]` 展开折叠面板，保留旧能力但不作为主路径：

- **坐标**：十进制输入 + 半球下拉（北纬 N / 南纬 S、东经 E / 西经 W），两组都带 `°` 单位后缀，复用现有 `.unit-input` / `.two-fields` 样式。正负号由下拉决定，用户不用记符号。
- **时区**：`UTC-12 … UTC+14` 下拉（含 `:30` / `:45` 档），与自动推导值不一致时明确显示「自动推导为 UTC+9，你改成了 UTC+8」。
- 面板顶部有「恢复自动推导」按钮，一键回到地点库结果。
- **DMS 输入**（G2）：`31°13′49″N` 与 `31.2304` 双向换算，粘哪边都行。
- **海拔**（G3）：`elevation_m`，默认 0，可留空。

### 4.4 时区与夏令时推导（G1，本方案的核心技术点）

推导链：`place_id → IANA 时区名 → 按出生日期求该时刻的实际偏移`。服务端用 Python 标准库 `zoneinfo`，本地计算，不联网。实测 `datetime.dst()` 可直接给出夏令时增量，因此**标准偏移无需额外查表**：

```
A（实际偏移）= tzinfo.utcoffset()        # 1990-05-20 上海 -> 540 分钟
D（夏令时）  = tzinfo.dst()              # -> 60 分钟
S（标准偏移）= A - D                     # -> 480 分钟
```

- 输出四项：`utc_offset_minutes`（整数）、`tz_name`、`dst_active`、`dst_transition`（该段的起止日期）。
- **证据行是必显项**，不是可选折叠：写清「什么时间、什么地方、得出多少」，并可展开看来源（时区库版本 + 切换日期）。文案示例见 §4.2，止日必须写成「1990-09-16 为止、09-17 恢复 UTC+8」，不能把切换日直接当成夏令时结束日。
- 用户手动改过偏移后，状态从「自动」变为「已手动校正」，显示 `UTC+8（已手动校正，自动推导为 UTC+9）`，且**不会**因为改动旁边的字段而被静默覆盖——只有点「恢复自动推导」才回到自动值。
- **置信度四级**（与地名库粒度对齐）：

| 值 | 含义 | G1 是否可达 |
| --- | --- | --- |
| `exact` | 区县级坐标（G2 中国区县库） | 否 |
| `city` | 城市级代表点（G1 `curated`） | **是（G1 的常态）** |
| `approximate` | 仅国别，或由坐标反查最近城市得到 | 是 |
| `uncertain` | 出生时刻早于该时区的首个切换点，落在地方平时（LMT）段 | 是 |

- **`uncertain` 的判定是数据驱动的，不写死年份**：对 `Asia/Shanghai` 首个切换点是 `1901-01-01`（之前为 LMT `+8:05:43`），但各时区不同，实现必须按「该时区是否有早于出生时刻的切换点」判断。命中时提示「该日期当地使用地方平时（LMT），无法用整数分钟精确表达，请确认」。
- **已知精度边界**：引擎按整数分钟取偏移（`src/astro/astro_controller.cppm` 第 175 行 `input.at("utc_offset_minutes").get<int>()`）。LMT 段是秒级偏移（`Asia/Shanghai` 1900 年为 485.72 分钟），分钟取整带来 ≤30 秒误差（≈上升 0.007°）。证据行标注这一点，不假装精确。

### 4.5 城市级坐标的精度后果（G1 必读）

这是选择 `curated` 城市级数据换来的代价，必须在 UI 里交代清楚，否则「看起来精确」比「不精确」更危险。

实测本方案的敏感度（1990-05-20 14:00、UTC+9、上海 31.23°N、上升处女 16°）：

| 扰动 | 上升变化 | 天顶变化 |
| --- | --- | --- |
| 经度 +1° | +0.8596° | +0.9279° |
| 经度 −1° | −0.8592° | −0.9292° |
| 纬度 +1° | +0.1120° | 0.0000° |

结论：**经度误差几乎 1:1 传导到上升点（本盘 0.86），纬度误差影响小一个数量级（0.11）**。所以城市级代表点的风险主要来自东西向跨度：

- 行政范围 ~50 km 的地区 → 经度误差可达 ±0.25° → 上升误差约 ±0.2°；
- 行政范围数百公里的地区（如呼伦贝尔这类跨度极大的地级市）→ 上升误差可达 2° 以上，足以改变上升星座或宫位。

处理方式：`curated` 每条带一个 `approx_radius_km`；超过 50 km 的地点，卡片显示「该地点为城市级代表点，范围较大，建议微调到出生区县」。**G1 不做区县检索，所以这条提示的出口是「手动微调坐标」，不是「再搜一次」。**

（敏感度随上升星座与纬度变化，上表是本盘实测量值，不是普适常数；文案不要写成固定比例。）

### 4.6 软校验（G1，不阻断）

只在卡片证据行以 `⚠` 呈现，不弹窗、不禁用提交按钮——目的是提醒而不是打断：

| 规则 | 触发条件 | 文案 |
| --- | --- | --- |
| 偏移-经度不相容 | 经纬度已知，且 `|offset×15 − lon| > 30°` | 「经度 121.5°E 通常对应 UTC+8，当前为 UTC+0，请确认」 |
| 坐标疑似未填 | `|lat| < 0.5° 且 |lon| < 0.5°` | 「该坐标位于几内亚湾近海，通常是坐标未填写」 |
| 极区宫制 | `|lat| > 66°` 且宫制为 Placidus | 「Placidus 在极区可能无法计算，建议改用 Whole Sign」 |
| 夏令时未采纳 | 自动推导出夏令时，而用户手动改回标准时 | 「该日期当地处于夏令时（+60 分钟），当前按标准时计算」 |
| 城市级范围提示 | `approx_radius_km > 50` | 「该地点为城市级代表点，建议微调到出生区县」（§4.5） |

第三条与引擎侧校验一致（`src/astro/astro.cppm` 第 207 行 Placidus 极区检查），前置到 UI 是为了让用户在提交前就知道，而不是收到一个 `HOUSE_CALCULATION_FAILED`。

**刻意不做的校验**：「200 km 内没有地名」这类基于地名库密度的判断。G1 只有约 300 条城市数据，用它判「附近无地名」会对大量合法出生地误报（例如青海、西藏的县级出生地）。这条规则的成立前提是 G2 的中国区县全量库，G1 不启用。

### 4.7 状态机

```
        搜索并选中地名
  空 ──────────────────▶ 自动（auto）
                          │  ↓↑ 改坐标 / 改时区
                          ▼
                       已校正（manual）──[恢复自动推导]──▶ 自动

  手动填坐标（不走搜索）──▶ 未解析（unresolved）
                          │  反查最近城市仅作提示，不改变状态
                          ▼
                       未解析（地点名显示「约：最近城市」）
```

三种状态在地点卡上有明确视觉与文案区分，并原样写进「结构事实 / 解析提示词」页签的输入回显，保证可回溯。

### 4.8 记忆与分享（G2）

- `localStorage` 保存：最近 5 个地点、上次使用的坐标与时区、**用户对某地点的偏移修正**（键为 `place_id + 适用年份区间`）。下次选中同一地点时自动套用，并标注「沿用你上次的校正」。
- 「复制参数链接」：`/astro.html?place=curated:cn-shanghai&date=1990-05-20&time=14:00`，他人打开即还原（坐标与时区由 `place_id` 重新解析，不信任链接里的裸坐标）。
- 分享链接只带地名与时间，不带任何解读结论。

## 5. 全系统共用形态

### 5.1 两类消费者与字段映射

全系统 6 个页面的地点需求盘点（实测）：

| 页面 | 现有字段 | 是否需要经纬度 | 性质 |
| --- | --- | --- | --- |
| `astro.html` 西洋占星 | UTC 偏移分钟 + 纬度 + 经度 | 需要 | 绝对偏移 `A` + 坐标 |
| `bazi.html` 八字 | 经度 + 标准经线 + 夏令时 | 只需经度 | 真太阳时校正 |
| `index.html` 紫微斗数 | 经度 + 标准经线 + 夏令时 | 只需经度 | 真太阳时校正 |
| `qimen.html` / `liu-yao.html` / `da-liu-ren.html` | 无地点输入 | 否 | 暂不是消费者（奇门也用时辰，未来可接入） |

两组字段都能从同一次解析导出。依据是引擎里的真太阳时公式（`src/common/calendar/calendar.cppm` 第 189-192 行）：

```
真太阳时 = 记录时刻 − daylight_saving_minutes×60s + (经度 − 标准经线)×240s + 均时差
```

代入 `标准经线 = S/4`（1 小时 = 15°，即 4 分/度）、`daylight_saving_minutes = A − S`，结果正是 `记录时刻 − A + 经度×4分` = 地方平时，与西洋占星用的绝对偏移自洽：

| 中立解析结果 | → 西洋占星 | → 紫微 / 八字 |
| --- | --- | --- |
| `longitude` | `location.longitude` | `time_correction.longitude` |
| `latitude` | `location.latitude` | 不使用 |
| `actual_offset_minutes` = A | `utc_offset_minutes` = A | 经 `standard_meridian` 与 `daylight_saving_minutes` 间接表达 |
| `std_offset_minutes` = S | — | `standard_meridian` = S/4 |
| `dst_minutes` = A − S | 证据行 | `daylight_saving_minutes`（受 §5.4 约束） |
| `tz_name` / `dst_transition` | 证据行 | 证据行 |

也就是说：**同一个组件、同一次解析，两个消费者各自取自己那几个数**。

### 5.2 三层结构

| 层 | 交付物 | 职责 | 是否绑定命理类型 |
| --- | --- | --- | --- |
| 解析服务 | `web/geo_places.py` + `/api/v1/geo/*` | 地名检索、坐标解析、时区与偏移推导、校验 | 否 |
| 组件 | `web/place-picker.js` + `place-picker.css` | 搜索、候选、地点卡、证据行、警告、微调面板、状态机 | 否（靠配置） |
| 适配器 | 各页几行配置 | 声明「结果写进哪些 id / 显示哪些字段」 | 是 |

组件接口（示意）：

```js
createPlacePicker({
  mount: '#place-section',
  dateInput: '#astro-date',        // 日期一变就重新推导偏移
  mode: 'geo+offset',              // 或 'longitude+meridian+dst'
  outputs: {offset: '#astro-offset', lat: '#astro-lat', lon: '#astro-lon'},
  recentKey: 'astro.recentPlaces',
})
```

### 5.3 兼容策略：沿用旧 id

组件写回的输出控件**沿用现有 id**：

- 西洋占星：`astro-offset` / `astro-lat` / `astro-lon`
- 八字 / 紫微：`longitude` / `meridian` / `dst`

这样 `astro.js`、`bazi.js`、`app.js` 里的取值与 payload 构造**一行都不用改**，只是值的来源从「人手输入」变成「组件写入」。已验证的收益：

- `tests/test_bazi_web_contract.py` 第 44-46 行断言 `id="longitude"` / `id="meridian"` / `id="dst"` 存在 → 保 id 策略下继续通过；
- 该文件第 161-172 行的标定用例（`longitude 120.3 / standard_meridian 120.0 / daylight_saving_minutes 0`）直接调 CLI，不经 UI，完全不受影响；
- 紫微/八字页默认值 `120.3 / 120 / 0` 在默认日期 1994-12-08 上海本来就是对的（实测该日偏移 480、无夏令时），所以**默认案例与基线不动**，组件改的是其他日期与地点。
- 西洋占星页的 `#astro-offset` 等 id 没有任何测试断言（已核实），但保留它们仍然让 `astro.js` 第 485-487 行的提交逻辑保持原样。

**一个实现陷阱**：输出控件改为 `type="hidden"` 后**不能保留 `required`**——隐藏的必填控件在表单校验失败时会抛 "An invalid form control is not focusable" 且无法提交。改为在 JS 里校验并用 `setCustomValidity` 呈现。

### 5.4 字段约束与两个边界

引擎对真太阳时参数有硬约束（`src/common/calendar/calendar.cppm` 第 62-67 行）：`standard_meridian ∈ [-180, 180]`、`daylight_saving_minutes ∈ [0, 180]`。这带来两个必须处理的边界：

1. **负夏令时**：实测 `Europe/Dublin` 与 `Africa/Casablanca` 在冬季是 `A=0, S=60, DST=−60`（tzdata 把爱尔兰标准时定为 UTC+1，冬季算「负夏令时」）。`daylight_saving_minutes` 不接受负值，因此适配器在 `A < S` 时改取 `daylight_saving_minutes = 0`、`standard_meridian = A/4`。代入公式与取 `A−S` 完全等价，但 UI 仍显示真实的 `UTC+0`，不能把负夏令时写成 0 了事。
2. **极端东偏移的已知限制**：`standard_meridian = S/4` 在 `|S| > 720 分钟` 时超出 ±180 的合法区间（实测 `Pacific/Apia` S=780 → 195°，`Pacific/Kiritimati` S=840 → 210°）。把这些经线按 mod 360 折回（195 → −165）会引入 24 小时误差，**不是等价换算**。G2 接入紫微/八字时，对这类地点直接提示「该时区超出真太阳时校正的合法范围，已按标准时计算」，不静默降级。西洋占星页不受此限制（它用绝对偏移 `A`）。

### 5.5 接入分期

- **G1**：服务与组件按中立形态实现，只接西洋占星页。
- **G2**：接入紫微斗数页与八字页（共用同一组件，只换 `mode` 与 `outputs`）。顺带修掉这两页的同类 bug：在 `1990-05-20 上海` 这类日期，它们的夏令时下拉会填「无」，而 60 分钟误差有约 50% 概率把**时辰推错一格**（时辰边界每 2 小时一次，1 小时偏差落在边界内的概率约一半）。
- **G3**：区县检索、DMS、海拔、记忆与分享。

## 6. 数据设计

### 6.1 数据集与来源

当前仓库内**没有任何地名数据**（`data/` 下只有 `ephemeris/`），需要新建 `data/geo/`。

| 层 | 内容 | 规模 | 阶段 | G1 是否交付 |
| --- | --- | --- | --- | --- |
| `curated` | 手工精选常用城市 | 约 300 条 | G1 | **是（唯一数据源）** |
| `cn_admin` | 中国省 / 地级市 / 区县及驻地坐标 | 约 3.2k 条 | G2 | 否 |
| `world_cities` | 全球主要城市 | 约 5k → 15k 条 | G2 | 否 |

`curated` 的选点构成（合计 300）：直辖市与省会/首府 34、计划单列市与人口前列地级市 120、港澳台 20、全球首都 100、其他高频海外城市 26。

字段（`data/geo/places.schema.json`）：

```
id               "curated:cn-shanghai"         // 全局唯一、可回溯
name_zh          上海市
name_en          Shanghai
aliases          ["上海", "沪", "shanghai", "sh"]  // 历史名/简称/拼音，供搜索
admin1           上海市
country_code     CN
lat / lon        31.2304 / 121.4737            // 城市代表点
approx_radius_km 30                            // §4.5 范围提示用
tz               Asia/Shanghai                 // IANA 时区名
population       24280000                      // 排序权重，可空
level            city                          // G1 只有 city；district/poi 属 G2
source           curated
revision         数据集版本
```

`elevation_m` 只在 G3 引入，G1 不设该字段（§4.2）。

**来源与许可**：`curated` 由本项目按公开资料手工整理，不批量复制任何商业地图数据。**禁止**从高德/百度等商业地图抓取坐标——既不合许可，也与项目「不复制竞品资产」的口径冲突。G2 引入第三方数据（GeoNames 为 CC BY 4.0）时必须核对许可与署名要求，写入 `data/geo/README.md` 与接口的 `provenance`。

**坐标准确性校验**：`curated` 每条必须通过一条自动测试——用该条目的经纬度粗算 `lon/15`，与该时区标准偏移 `S/15` 的差值应在 ±2 小时（±30°）内。这能抓住符号写反、经纬度对调、坐标抄错一类错误；不通过则测试失败，不靠人眼。逐条人工复核仍要做，但机器先筛一遍。

### 6.2 体积与加载

- `curated` 300 条约 60-80 KB（估算）；G2 的 8k 条约 1.5-2 MB（估算，落地时实测）。服务端启动时一次性载入内存（搜索索引 + 按 `id` 的字典），无数据库。
- `data/geo/index.json` 记录 `revision`、`count`、各分片校验和；`/api/v1/geo/meta` 暴露 `geo.revision` 与 `geo.count`，便于确认线上用的是哪版数据。

### 6.3 搜索实现

- 归一化：去空格、全角转半角、大小写折叠。
- 匹配：中文子串 / 拼音全拼前缀 / 拼音首字母前缀 / 英文前缀；四类命中给不同权重，叠加行政级别与人口权重。
- 300 条数据下顺序扫描即可；G2 换 8k 条后若单次超过 50ms 再加前缀树，不预先复杂化。

### 6.4 时区数据与依赖

- 运行时用 Python 标准库 `zoneinfo`（`utcoffset()` / `dst()` 取实际偏移与夏令时增量，§4.4）。无需第三方依赖，不联网。
- **版本必须固定并可报告**。实测本机 `zoneinfo.TZPATH` 首项指向 conda 的 `.../miniforge3/share/zoneinfo`（该目录**没有** `+VERSION`），而系统 `/usr/share/zoneinfo/+VERSION` 是 `2026c`——两者可能不是同一份数据，且 Docker 里又是 apt 装的第三份。开发机、CI、容器读到不同时区库而无人察觉，正是这类功能最难查的故障。因此：
  1. 引入 pip 包 `tzdata`（提供 `tzdata.IANA_VERSION`，落地时确认该常量名）；
  2. 用 `zoneinfo.reset_tzpath([...])` 把数据目录**固定到该包**，让三处环境读同一份；
  3. `/api/v1/geo/meta` 与解析结果的 `provenance` 都报告这个版本号；
  4. 版本取不到时报告 `"unknown:<路径>"`，**不编造版本号**。
- **Docker 要改两处**（当前 `Dockerfile` 只 COPY 了 `data/ephemeris`）：
  1. 新增 `COPY --from=builder /src/data/geo ./data/geo`；
  2. 依赖装 `tzdata`（pip 或 apt 均可，与上面第 1 条一致）。
- **兜底**：时区数据不可用时，`place-resolve` 返回 `tz_available: false` 并附 `utc_offset_minutes: null`，UI 退回「手动选时区」；地名搜索与坐标解析不受影响——不能因为时区库缺失导致整个表单不可用。

## 7. 接口设计

只读、无副作用，沿用现有的 `send_api_success` 与错误码约定。**命名空间是 `/api/v1/geo/`，不是 `/api/v1/astro/`**——地名与时区不是占星专属概念（§5.1）。

| 方法 | 路径 | 入参 | 出参 |
| --- | --- | --- | --- |
| GET | `/api/v1/geo/places` | `q`、`limit`（默认 20，上限 50）、`country`（可选） | 候选列表（`display`、上级行政区、坐标、`tz`） |
| POST | `/api/v1/geo/place-resolve` | `{place_id}` 或 `{query}` 或 `{latitude, longitude}`，加 `{date:{year,month,day}}`、可选 `{utc_offset_minutes, house_system}` | §6.5 的 `PlaceResolution`（含 `warnings`） |
| GET | `/api/v1/geo/meta` | — | `{revision, count, tzdata_version, tz_available}` |
| GET | `/api/v1/astro/meta`（扩展） | — | 增加 `geo: {...}` 复用上面同一份数据，保持天文页签自洽 |

**已定：`location-check` 并入 `place-resolve`**，只新增 3 个端点。理由是手动坐标路径本质上也是「一次解析」——入参给 `latitude/longitude` 而非 `place_id`，出参同样需要 `warnings` 与 `provenance`；拆开会迫使前端在两条路径上维护两套校验逻辑。`place-resolve` 因此有三选一的入参形态，后者的 `place` 可能为空（`nearest_place` 未命中），但 `time`、`warnings`、`provenance` 始终返回。

错误码（与既有约定一致，404 已被 `SHEN_SHA_NOT_FOUND`、`AI_REVIEW_NOT_FOUND` 使用）：

- `400 INVALID_REQUEST`：`q` 缺失/超长、`limit` 越界、日期非法；
- `404 PLACE_NOT_FOUND`：`query` / `place_id` 无匹配；
- `500 GEO_CONFIG_ERROR`：`data/geo/` 缺失或 schema 不符（与既有 `*_CONFIG_ERROR` 命名一致）。

**契约不动的地方**：`/api/v1/astro/charts`、`/natal-analysis`、`/natal-reading` 的请求体与响应结构都不改；地点信息只存在于前端与解析接口之间。

## 11. 已确认决策

| 决策 | 结论 | 对方案的约束 |
| --- | --- | --- |
| 地名库范围 | **`curated` 约 300 条先跑通** | G1 不引入第三方数据、不做许可署名流程；接口与 `provenance` 按全量库形态设计，G2 换库不改契约；代价是精度只到城市级，用 §4.5 的提示与 §6.1 的自动校验兜住 |
| 主路径形态 | **地名搜索为唯一主路径** | 三个裸数字输入退出表单主层，降级为「微调」折叠面板；UTC 偏移不再由用户直接填写 |
| 默认案例 | **默认值不动，由证据行标出** | 保留 `1990-05-20 / 14:00 / 上海 / 480`；首屏即展示「当时处于夏令时，应为 UTC+9，且这正是现默认值的错误」；`curated` 里上海市坐标取同一组值，205 项测试与 N1-N4 基线零改动 |
| 共用范围 | **接口与组件中立，G1 只落西洋占星** | 服务挂 `/api/v1/geo/*`；组件与样式独立成文件、不写进 `astro.css`；输出沿用旧 id 以免动三页的 payload 代码；紫微/八字留 G2 |
| 端点数量 | `location-check` 并入 `place-resolve` | 新增 3 个端点（places / place-resolve / geo-meta） |
