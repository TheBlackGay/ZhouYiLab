# ZhouYiLab 版本管理规范

> 当前项目版本：`3.0.0`
> 生效日期：`2026-08-31`（版本记录最后更新：2026-09-20）

## 1. 版本格式

项目版本统一使用：

```text
主版本.功能版本.修订版本
MAJOR.MINOR.PATCH
```

例如：`1.1.0`、`1.2.0`、`1.2.1`。

## 2. 升级规则

### 2.1 功能大改

新增完整功能、进行较大范围改造或形成新的业务能力时，递增功能版本，并把修订版本归零。

```text
1.1.0 → 1.2.0 → 1.3.0
```

适用示例：

- 新增完整命盘分析引擎；
- 将现有功能改造成前后端分离接口；
- 新增完整术数模块；
- 对核心计算或数据结构进行较大改造。

### 2.2 Bug 修复与小优化

修复缺陷、调整文案、优化局部性能或进行不改变主体能力的小范围改进时，递增修订版本。

```text
1.1.0 → 1.1.1 → 1.1.2
```

适用示例：

- 修复某个流月宫位计算错误；
- 修正接口字段或错误提示；
- 优化页面局部布局；
- 补充少量格局配置，但不改变分析架构。

### 2.3 主版本升级

发生整体架构替换、核心算法或公共契约大面积不兼容时，递增主版本，并将后两位归零。

```text
1.9.3 → 2.0.0
```

主版本升级必须在实施前确认迁移范围，不能仅因为功能数量增加而随意升级。

## 3. 分支与提交

版本分支统一使用：

```text
r_<版本号>
```

例如：

```text
r_1.1.0
r_1.1.1
r_1.2.0
```

提交信息应描述该版本的主要结果：

```text
feat: release ZhouYiLab 1.1.0 API foundation
fix: release ZhouYiLab 1.1.1 calculation corrections
```

## 4. 发布时必须同步

每次创建版本分支并提交前，必须同步检查：

1. 根目录 `CMakeLists.txt` 的 `project(... VERSION ...)`；
2. HTTP API 返回的 `algorithm_version`；
3. 相关接口或功能文档的版本号；
4. 示例程序与自动化测试；
5. Git 分支名是否与项目版本一致；
6. 工作区是否包含不属于本版本的文件。

## 5. 项目版本与 API 版本

项目版本和 HTTP API 路径版本不是同一个概念：

- 项目可以从 `1.1.0` 升级到 `1.2.0`，接口仍保持 `/api/v1`；
- 只要 `/api/v1` 继续保持向后兼容，就不需要升级 API 路径；
- 只有接口出现无法兼容的字段或语义变化时，才新增 `/api/v2`；
- 旧 API 应保留迁移期并明确标记废弃时间。

## 7. CI/CD 门禁（2026-09-21 实况记录）

DEF-8 治理修正后，闸门模型如下（描述现行事实，不改 §4 六项同步要求）：

| 闸 | 触发 | 内容 | 首证 |
| --- | --- | --- | --- |
| Python Tests | `main`/`master`/`r_*` 全部 push/PR + 手动 dispatch | 作业内构建 7 个网页 CLI（ubuntu-24.04 + llvm-19，Release）→ 语法闸 → 全量 unittest → `check_calibration`（permissive；发布前本机 --strict） | b40b94d 起连续多绿 |
| Docker Smoke | 任意分支命中镜像相关路径（Dockerfile/web/config/src/cmake/data 等） | 镜像构建 → 起容器 → health 等待 → 核心 API 冒烟 | b40b94d 历史首绿（DEF-8 bind/梅花目标双修后） |
| Clang/LLVM Build | main + dispatch | 三版本 clang 矩阵 × 双 build 型，全目标构建 | 24.04 配方有 python-tests 与 docker builder 双实证，待 main 合并日实测 |
| MSVC Build | main + dispatch | Windows 矩阵 | windows-2022 退役风险未迁（台账 C4 待验证） |

- 日常主干（当前 `r_3.0.0`）由前两闸持续把关；重型编译矩阵集中在发布合并时点；
- 不发明 tag 惯例（§6 注记）：发布以 `r_<version>` 分支顶端 + §4 六项同步为准，
  GitHub Release 与否由人工决定；
- 红线：门禁只增不废；任一闸红头的提交不得合入 main。
